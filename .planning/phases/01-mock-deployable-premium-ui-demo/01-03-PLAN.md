
URL-keyword routing rules (CONTEXT.md D-13 — verbatim):
- `/fail/i.test(url)` → emit `{type:"stage", stage:"fetching"}` → sleep 500ms → emit `{type:"error", code:"NETWORK", message:"We couldn't reach the extraction service."}`
- `/empty/i.test(url)` → emit `fetching` → sleep 700ms → emit `transcribing` → sleep 700ms → emit `{type:"error", code:"NO_WORKOUT", message:"We couldn't find an exercise routine in this video."}`
- `/rate-limit/i.test(url)` → sleep 300ms → emit `{type:"error", code:"RATE_LIMITED", message:"You've extracted a lot of workouts recently."}`

Error-state UI copy (verbatim from UI-SPEC §7.4):
- INVALID_URL inline (handled by UrlInput, NOT ErrorState): heading none, body "That doesn't look like a YouTube link. Try a URL from youtube.com or youtu.be.", action: correcting clears
- NETWORK: heading "Something went wrong on our end.", body "We couldn't reach the extraction service. Check your connection and try again.", action "Try again" (dispatch reset + refocus input with URL retained)
- NO_WORKOUT: heading "No workout in this video.", body "We couldn't find an exercise routine in this video. Try a clearly-narrated workout video — like an instructor calling out sets, reps, and form cues.", action "Try another URL" (dispatch reset, clear input)
- RATE_LIMITED: heading "Slow down for a moment.", body "You've extracted a lot of workouts recently. Wait a minute and try again.", action "Got it" (dispatch reset, clear input)

| Additional fixture files | Build-time-trusted; same module-load `WorkoutSchema.parse()` gate as Plan 01-01's single fixture (T-01-03 inherited). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | The four new fixture JSON files — schema drift during edits | mitigate | All 5 fixtures included in `tests/schema.test.ts` (extended in Task 1 of this plan); CI runs `pnpm test` which fails the build if any fixture fails `WorkoutSchema.parse`. Inherits T-01-03 from Plan 01-01. |
| T-02-02 | Information Disclosure | URL-keyword routing visible in production logs | accept | Demo URLs are intentionally public; the keyword routing is a feature, not a bug. The `error` events emit user-friendly `message` strings only; no stack traces, no internal state. Real-world abuse of this is low-impact (worst case: someone discovers the demo URLs, which is the intended UX). |
| T-02-03 | Spoofing | Real YouTube videoID containing substring `fail` / `empty` / `rate-limit` | accept | YouTube IDs are 11 chars of `[A-Za-z0-9_-]`; collisions with these substrings are possible but vanishingly unlikely (RESEARCH §"Assumption A4"). Phase 1 doesn't surface this as a failure mode — if it ever happens, the user retries with the same URL because the keyword matches inside the URL string, not just the videoID, and most users will paste with full URL context. |
| T-02-04 | Tampering | Inline URL validation bypass via DOM tampering | accept | Client-side validation is a UX defense, not a security control. The server already validates via `ExtractRequestSchema.safeParse(body)` at the route handler (T-01-01 from Plan 01-01). Bypassed inline validation still produces a valid `https://...` URL that the mock service handles or, if invalid, that the server rejects with 400. |
</threat_model>
