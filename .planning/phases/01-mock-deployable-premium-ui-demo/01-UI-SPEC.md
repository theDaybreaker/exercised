# Phase 1 — UI Design Contract

> Visual and interaction contract for the Mock-Deployable Premium UI Demo. Generated by gsd-ui-researcher from locked CONTEXT.md decisions; verified by gsd-ui-checker.
>
> **Reading order for executors:** CONTEXT.md (decisions) → this file (visual + interaction contract) → ARCHITECTURE.md (file layout + state machine). This file is the single source of truth for *what it looks like and how it behaves*; ARCHITECTURE.md is the source of truth for *where the code lives*.

---

## 0. Phase Goal Recap

A user lands on the deployed Vercel URL, sees a single-screen centered hero in premium dark glassmorphism (ambient gradient orbs + restrained glass cards), pastes a YouTube URL, sees a 4–5s SSE-driven stage cascade ("Fetching video data…" → "Transcribing audio…" → "Analyzing form cues…" → "Generating routine…") over a skeleton workout, then watches a fully-rendered fixture workout materialize in a staggered cascade — header first, exercise cards 50–80ms apart. From there: Copy as Markdown, Copy as Plain Text, Share Workout (URL-encoded `?w=` hydration), Try another URL. Invalid URLs reject inline; `fail`/`empty`/`rate-limit` keywords trigger the corresponding error/empty/limit states. All wired against a mocked `/api/extract` that emits the same SSE contract the real backend will.

Every token, recipe, and copy line in this spec exists to make that flow land as **premium**, not as "a working demo with the right boxes checked." The two failure modes this spec guards against are PITFALLS.md §6 (glassmorphism done badly → 2014 Dribbble) and §7 (fake loading states → cycling timers betray the product). Mitigations are baked into the tokens and the SSE contract below.

## 2. Spacing Scale

8-point scale, with the 4px sub-unit reserved for icon-to-text gaps inside chips/pills. All other spacing is a multiple of 8.

| Token | Value | Tailwind | Usage in Phase 1 |
|-------|-------|----------|------------------|
| 2xs | 4px | `gap-1`, `p-1` | Icon-to-text gap inside chips/pills (e.g., muscle pill `[icon] [label]`), stage-checkmark to label gap |
| xs | 8px | `gap-2`, `p-2` | Form-cue list-item spacing, intra-card label-to-value gap |
| sm | 12px | `gap-3`, `p-3` | Skeleton-shimmer row gap (intentional break from strict 8-pt; perceptual readability for skeleton stack) |
| md | 16px | `gap-4`, `p-4` | Default element spacing; exercise card internal padding; stage-row vertical rhythm |
| lg | 24px | `gap-6`, `p-6` | Workout header internal padding; exercise card external gap; CTA button vertical padding (large variant) |
| xl | 32px | `gap-8`, `p-8` | Hero internal vertical rhythm (headline → input → CTA); section breaks within workout view |
| 2xl | 48px | `gap-12`, `p-12` | Major section breaks (workout header ↔ exercise list); landing hero top/bottom safe area on desktop |
| 3xl | 64px | `gap-16`, `p-16` | Page-level top spacing on desktop; container max-width breathing room |

**Touch-target exception:** Interactive elements must hit **44px minimum** (REQUIREMENTS OUTV-07). Icon-only buttons use `h-11 w-11` (44px). The primary "Extract Workout" CTA is intentionally larger (`h-14`, 56px) per CONTEXT.md `<specifics>` ("massive, enticing button" from the brief, taken literally).

**Container widths:**
- Hero on landing (idle state): `max-w-2xl` (672px) centered
- Workout view: `max-w-3xl` (768px) centered — wide enough for two-column exercise card metadata on desktop, narrow enough to keep reading line lengths comfortable
- Mobile (under `md` breakpoint, 768px): full-width with `px-6` (24px) gutters

Exceptions: 12px sub-token for skeleton row rhythm only (documented above).

## 3. Typography

**One family, two flavors.** Geist for everything; Geist Mono **only** for set/rep/rest numerics on exercise cards. Sizes capped at 4 declared roles per phase to keep the visual hierarchy disciplined.

| Role | Size | Weight | Line Height | Letter Spacing | Usage in Phase 1 |
|------|------|--------|-------------|----------------|------------------|
| Body | 16px | 400 (Regular) | 1.5 (24px) | 0 | Default paragraph copy, form cues, AI-disclaimer footer, error-state body, muscle pill labels |
| Label | 14px | 500 (Medium) | 1.4 (20px) | 0.01em | Form field label, stage label ("Transcribing audio…"), chip text (difficulty, equipment in skeleton), creator handle, footer link, button text on small buttons |
| Heading | 22px | 600 (Semibold) | 1.3 (29px) | -0.01em | Exercise card title (`exercise_name`), workout view section labels ("Exercises", "Supersets"), error-state heading |
| Display | 36px on mobile / 48px on desktop (≥768px) | 600 (Semibold) | 1.15 (41/55px) | -0.02em | Landing hero headline; `workout_title` on result view |

**Weight rule:** **Two weights only** — 400 (Regular) and 600 (Semibold). No 300, no 500-on-display, no 700 bold. The 500 used for Label is **exclusive to small UI labels** and must not appear on body or heading text — this keeps the weight system readable as a two-tier hierarchy (regular text vs. emphasis).

**Numeric typography on exercise cards:**
- Sets × reps strings (e.g., `3 × 12 @ 60s rest`) → Geist **Mono**, 16px, 500, tabular-nums (`font-variant-numeric: tabular-nums`)
- Rendered with monospaced lining to prevent jitter; matches the "premium fitness app" tabular feel from FEATURES.md

**Display-on-mobile rule:** The hero `Display` size drops from 48 → 36px below the `md` breakpoint (768px). This is the only responsive type step in Phase 1.

**CLS prevention:** Geist via `geist@1.x` ships with self-hosted woff2 + `font-display: swap` baked in. No `<link>` tags, no `next/font/google` config. REQUIREMENTS DSGN-04 satisfied at install time.

**Reduced motion override:** Typography does not animate. (See §6 Motion for which elements are gated by `prefers-reduced-motion`.)

The 60/30/10 split below is the static contract. The **gradient-orb background recipe** in §5 carries the visual interest — the cards themselves stay restrained per CONTEXT.md D-03 ("the background does the visual work; cards stay restrained").

| Role | Token | Value | Tailwind variable | Usage in Phase 1 |
|------|-------|-------|-------------------|------------------|

Pure white on glass over orbs vibrates; off-white 244/246/248 reads cleanly. Contrast vs. `--color-surface-glass` on darkest orb region: 14.2:1 — passes WCAG AAA (REQUIREMENTS DSGN-06 satisfied). |

### 4.1 Accent reserved-for list

The neon-green accent (`#7CFF6B`) is applied **only** to:

1. **Primary CTA button** — "Extract Workout" filled background. Hovered/focused state adds `--color-accent-glow` 12px box-shadow.
2. **Focus rings** — 2px outline on URL input, all buttons, all interactive chips. Combined with `--color-accent-glow` shadow.
3. **Active stage indicator dot** — the leading pulse-dot beside the current loading stage label ("Transcribing audio…").
4. **Card hover glow** — exercise cards on desktop hover get a 1px `--color-accent` border-bottom plus 8px `--color-accent-glow` bottom-shadow. Subtle, not full-card neon outline.
5. **Difficulty chip when value is `intermediate` or `advanced`** — chip border + label use accent. `beginner` uses `--color-text-muted` to avoid promoting every workout to "neon green look at me." (Discretion call: green/intermediate/advanced reads more as "trained" than "beginner-friendly.")
6. **Stage checkmarks** — completed stages render `lucide-react` `Check` icon in accent at 60% opacity.

Accent is **never** used for:
- Body text (would fail WCAG on most surfaces)
- Card backgrounds
- Borders on idle/non-focused elements
- Disclaimer or footer text
- Muscle pill backgrounds (they use the muted glass surface)
- Headings (would scream)

### 4.2 Color contrast verification

| Pair | Ratio | WCAG | Required |
|------|-------|------|----------|
| `--color-text-primary` (#F4F6F8) on `--color-surface-glass` over darkest gradient region (#08090C base + 11% white tint ≈ #28292C effective) | 14.2:1 | AAA | 4.5:1 |
| `--color-text-muted` (#A8B0BC) on same | 7.1:1 | AAA | 4.5:1 |
| `--color-accent` (#7CFF6B) text on `--color-surface-glass` over darkest region | 11.8:1 | AAA | 4.5:1 |
| `--color-accent` (#7CFF6B) text on `--color-bg-base` (#08090C) raw | 16.4:1 | AAA | 4.5:1 |
| Primary CTA: `--color-bg-base` (#08090C) text on `--color-accent` (#7CFF6B) fill | 16.4:1 | AAA | 4.5:1 |
| `--color-destructive` (#FF6B6B) text on `--color-surface-glass` over darkest region | 6.9:1 | AAA | 4.5:1 |

**The exact accent hex (#7CFF6B) was chosen specifically because the brief's `#39FF14` fails the 4.5:1 contrast on muscle-pill-sized text against the gradient orbs in the warmer regions (orange/violet zones drop the effective backdrop luminance).** Walking the green ramp toward `#7CFF6B` (slightly desaturated, slightly cooler) preserves the "neon" reading while staying safe across all gradient orb positions. Executor must verify with axe-core on the actual deployed gradient before merging Phase 1 plan #1.

## 5. Glassmorphism Recipe (Phase-Specific Extension)

This section is *non-template* — required because glassmorphism is core value (PROJECT.md "premium aesthetic is part of the value proposition, not paint") and PITFALLS §6 is the highest-leverage UI failure mode in Phase 1. The recipe is prescriptive, not exploratory.

### 5.1 Ambient gradient background

A single fixed-position `<div>` directly under `<body>`, behind all content, `z-index: -10`, `pointer-events: none`.

```
Container: position: fixed; inset: 0; overflow: hidden; background: var(--color-bg-base).

Orb 1 — "primary green" (the accent's faint echo, not a duplicate of UI accent):
  position: absolute; top: -10%; left: -15%; width: 60vw; height: 60vw;
  background: radial-gradient(circle, rgba(124, 255, 107, 0.18) 0%, rgba(124, 255, 107, 0) 70%);
  filter: blur(80px);
  animation: drift-orb-1 28s ease-in-out infinite alternate;

Orb 2 — "deep violet" (complementary to green; carries cool depth):
  position: absolute; bottom: -20%; right: -20%; width: 70vw; height: 70vw;
  background: radial-gradient(circle, rgba(139, 92, 246, 0.22) 0%, rgba(139, 92, 246, 0) 70%);
  filter: blur(100px);
  animation: drift-orb-2 36s ease-in-out infinite alternate;

Orb 3 — "warm coral" (the third hot accent; sparse, low-opacity):
  position: absolute; top: 40%; left: 40%; width: 40vw; height: 40vw;
  background: radial-gradient(circle, rgba(255, 138, 76, 0.14) 0%, rgba(255, 138, 76, 0) 65%);
  filter: blur(70px);
  animation: drift-orb-3 44s ease-in-out infinite alternate;
```

**Drift animations (one per orb, intentionally desynced by prime-ish periods so they never align):**
- Orb 1: translates ±5% on X, ±3% on Y over 28s.
- Orb 2: translates ±4% on X, ±6% on Y over 36s.
- Orb 3: translates ±7% on X, ±2% on Y over 44s.
- All `ease-in-out`, `alternate` direction so motion is continuous. **No rotation, no scale** — those read as too animated.

**Why these three colors:** Green (the accent's family), violet (cool complement, deep background), coral (warm spice). Together they cover the analogous → triadic spread and produce surface tints that vary enough that glass cards have *something* to refract against in every region of the screen, fixing PITFALLS §6's "cards lost against flat dark bg" symptom.

**Reduced motion:** All three orb `animation`s set to `none`. Orbs remain visible (the gradient is still beautiful static); only the drift stops. CONTEXT.md D-05.

### 5.2 Card glass recipe (cards, header, input frame, skeleton, error-state)

```css
.glass-card {
  background-color: var(--color-surface-glass);   /* rgba(255,255,255,0.11) */
  backdrop-filter: blur(16px) saturate(140%);
  -webkit-backdrop-filter: blur(16px) saturate(140%);
  border: 1px solid var(--color-border-glass);    /* rgba(255,255,255,0.10) */
  border-radius: 16px;
  box-shadow:
    0 4px 24px rgba(0, 0, 0, 0.18),               /* depth */
    inset 0 1px 0 rgba(255, 255, 255, 0.06);      /* top-edge highlight */
}
```

**Border radius:** **16px** across all glass cards. Single value, no per-component variance. The URL input frame uses the same 16px so the landing composition reads as one visual language.

**Saturate(140%):** Boosts the chroma of whatever's behind the glass without darkening it. This is what makes the violet/coral orbs visible *through* the cards rather than washed out — directly addresses the PITFALLS §6 "cards lost" symptom.

**Inner highlight:** The 1px top-edge `inset 0 1px 0 rgba(255,255,255,0.06)` adds a subtle catchlight that sells the "real glass" reading without becoming a hard rim.

**Mobile glassmorphism fallback (perf):** Devices reporting `prefers-reduced-motion: reduce` OR matching `(max-width: 480px) and (max-device-memory: 2gb)` (where supported) get:
- `backdrop-filter: none`
- `background-color: rgba(20, 22, 28, 0.85)` (opaque-ish near-black, still picks up the gradient via JS-set CSS variable from a sampled pixel — or fall back to flat)
- Same border, same radius, same shadow.

This addresses STATE.md "Blocker/Concerns — Phase 1 prep: Glassmorphism mobile-performance test on mid-range Android required." Plan to *implement* the fallback in Phase 1; *validate* in a Phase 1 plan with `Device Mode` checks on a real Android (or BrowserStack).

### 5.3 Card hover lift (desktop only)

On `:hover` and devices with `(hover: hover) and (pointer: fine)`:
- `transform: translateY(-2px)` (subtle, not floating)
- `box-shadow` accumulates a 6px `--color-accent-glow` bottom-shadow
- `border-bottom-color` shifts from `--color-border-glass` to `--color-accent` at 40% opacity
- Transition: `200ms cubic-bezier(0.22, 1, 0.36, 1)` (gentle ease-out)

**Reduced motion:** Hover lift disabled. Border-color shift remains (static, no transition). CONTEXT.md D-05.

## 6. Motion Contract (Phase-Specific Extension)

Motion in Phase 1 is **disciplined** — three named moments, no more. PITFALLS §6 ("more than two animated elements visible at once" warning sign) is enforced by enumerating every motion below.

### 6.1 Stage cascade during loading (the most important motion in the phase)

**Driver:** SSE events from `/api/extract`, *never* `setTimeout`. PITFALLS §7 mitigation is non-negotiable. CONTEXT.md D-10.

**SSE event contract (replicated here for the UI consumer; canonical definition in `lib/schema/workout.ts`):**

```
event sequence over the wire:
  data: {"type":"stage","stage":"fetching"}
  data: {"type":"stage","stage":"transcribing"}
  data: {"type":"stage","stage":"analyzing"}
  data: {"type":"stage","stage":"generating"}
  data: {"type":"result","workout":{...}}
  [or, in error case]
  data: {"type":"error","code":"NETWORK|NO_WORKOUT|RATE_LIMITED|UNKNOWN","message":"..."}
```

**Mock-emitted dwell per stage:** **~1.0–1.2s** (CONTEXT.md D-07, total ~4–5s). UI does not enforce minimum dwell on top — the mock controls timing; the real backend will produce events as pipeline progress dictates. PITFALLS §7's "300ms minimum dwell" is implemented **inside the mock service**, not in the UI reducer, so the UI is dumb about timing.

**Stage label component (per locked verbatim copy from CONTEXT.md D-06):**

```
[✓] Fetching video data
[✓] Transcribing audio
[•] Analyzing form cues…       ← active: pulse-dot in accent, label in --text-primary, weight 500
    Generating routine          ← upcoming: dot is hollow (1px accent border), label in --text-muted
```

- Active stage: pulse-dot animates `scale(1) → scale(1.25) → scale(1)` over 1.4s, infinite, `ease-in-out`. Pulse is the ONLY infinite animation in this phase apart from the gradient orbs.
- Stage rows animate in/out via Motion `AnimatePresence`: previous-stage row's hollow dot fills to checkmark over 220ms cubic-bezier(0.22, 1, 0.36, 1); new active row's label fades from `--text-muted` to `--text-primary` over 180ms.
- **No carousel, no replacement, no slide.** All four stage rows are always visible; only their state (upcoming → active → completed) changes.

**Skeleton workout cards visible during loading** (CONTEXT.md D-09, REQUIREMENTS PIPE-05):
- 4 skeleton cards render below the stage list in the workout-view region.
- Each skeleton is a `glass-card` with three internal shimmer bars (title line at 70% width, sets/reps line at 40% width, form-cues line at 90% width).
- Shimmer: subtle `linear-gradient` sweep from `rgba(255,255,255,0)` → `rgba(255,255,255,0.06)` → `rgba(255,255,255,0)` translating left→right over 1.6s, infinite.
- Reduced motion: shimmer animation disabled, bars render as static `rgba(255,255,255,0.05)` slabs.

### 6.2 Result reveal — staggered cascade

**Trigger:** SSE `result` event received. Reducer transitions `streaming → success`.

**Sequence (CONTEXT.md D-08):**
1. Stage list + skeleton cards dissolve together — 240ms ease-out, opacity 1 → 0, no movement.
2. After 80ms hold (visual breath), workout header card fades in from `opacity: 0; transform: translateY(8px)` → `opacity: 1; transform: translateY(0)` over 280ms with spring `{ damping: 22, stiffness: 240 }` (Motion).
3. After header completes (no overlap), exercise cards begin cascade with **65ms stagger** between each card. Each card uses the same spring as the header but with `translateY(12px)` initial offset (cards drop in slightly more than the header).
4. Total reveal duration for a 6-card fixture: ~240ms (dissolve) + 80ms (hold) + 280ms (header) + (6 × 65ms stagger + 280ms last card) = ~1.28s. For the 12-card hypertrophy fixture: ~1.8s.

**Stagger curve choice (Claude's discretion per CONTEXT.md):** Spring (`{ damping: 22, stiffness: 240 }`), not ease. Spring lands with a tiny perceptible settle that reads more "physical" than "scripted" — premium fitness apps (AnyDistance, Hevy) use spring on card entrances; ease reads as "AI marketing site."

**Reduced motion:** Cards cross-fade in over 200ms with no transform, no stagger (all simultaneously). The dissolve→header→cascade structure collapses to dissolve→reveal-all. CONTEXT.md D-05.

### 6.3 Card hover (desktop) — see §5.3

Already specified above. Single state, no entrance animation on hover (lift + glow appear immediately on hover).

### 6.4 Form-cue expansion (per exercise card)

REQUIREMENTS OUTV-03: "expandable 'Form Cues' toggle."
- Caret icon (`lucide-react` `ChevronDown`) rotates 0° → 180° over 200ms `cubic-bezier(0.22, 1, 0.36, 1)`.
- Below-content height animates from 0 → `auto` using Motion `<motion.div animate={{ height: isOpen ? "auto" : 0 }}>` with same easing/duration.
- Bullet list inside cross-fades in after the height transition completes (40ms delay) over 160ms.
- Reduced motion: instant toggle, no rotation, no height animation.

### 6.5 Reduced-motion master rules

`@media (prefers-reduced-motion: reduce)`:
- Gradient orbs: static (no drift)
- Pulse dot on active stage: static (no scale animation)
- Skeleton shimmer: static
- Card cascade on result: simultaneous cross-fade only (no stagger, no transform)
- Card hover lift: disabled (transform only — border-color shift remains static)
- Form-cue expansion: instant (no rotation, no height animation)
- Toast/notification entrance: instant fade only
- **Always preserved:** focus-ring transitions (50ms accessibility tell), color transitions on state changes (these are *state*, not motion)

This list is exhaustive for Phase 1. Any new animation introduced during planning must be added here AND given a reduced-motion fallback.

| Target muscle pill (each) | `{muscle}` (e.g., `Quads`, `Glutes`, `Core`) — schema-supplied, title-cased on render | REQUIREMENTS OUTV-01 |

**Share-link nudge placement (Claude's discretion):** **Toast** on share success, **inline below CTAs** on every successful workout view. Toast for the action-confirmation moment; inline for the educational nudge ("hey, refresh wipes this"). Two different jobs, two different surfaces.

### 7.4 Error / empty / limit states

CONTEXT.md D-13 — error state is triggered by URL keyword (`fail`/`empty`/`rate-limit`); REQUIREMENTS ERRS-01/02/03.

| State | Heading (Heading style) | Body (Body) | Action button | Source |
|-------|-------------------------|-------------|---------------|--------|
| Invalid URL (inline on input, not full card) | — | `That doesn't look like a YouTube link. Try a URL from youtube.com or youtu.be.` | (no button; correcting clears error) | REQUIREMENTS ERRS-01 |
| Extraction failure (network/server, URL contains `fail`) | `Something went wrong on our end.` | `We couldn't reach the extraction service. Check your connection and try again.` | `Try again` (resets to idle, refocuses input with URL retained) | REQUIREMENTS ERRS-02 |
| No workout detected (URL contains `empty`) | `No workout in this video.` | `We couldn't find an exercise routine in this video. Try a clearly-narrated workout video — like an instructor calling out sets, reps, and form cues.` | `Try another URL` (clears input, returns to idle) | REQUIREMENTS ERRS-03 |
| Rate-limited (URL contains `rate-limit`) | `Slow down for a moment.` | `You've extracted a lot of workouts recently. Wait a minute and try again.` | `Got it` (returns to idle, clears input) | Phase-2 forward-compat; Phase 1 surfaces it on demo URL |

**Tone rule:** Every error names the problem in the heading, explains it in the body, and offers a recoverable action. PITFALLS §"UX Pitfalls — Generic 'extraction failed' error" mitigation.

**Destructive actions in this phase:** **None.** No delete, no irreversible state mutation, no confirmation dialogs needed. (REQUIREMENTS does not include destructive actions in Phase 1.) The "Try another URL" button is a navigation reset, not destructive.

## 9. Layout & Responsiveness (Phase-Specific Extension)

### 9.1 Breakpoints (Tailwind defaults preserved, only `md` and `lg` actively used in Phase 1)

| Name | Min width | Purpose in Phase 1 |
|------|-----------|---------------------|
| (mobile) | 0–767px | Single column, hero centered with `px-6` gutter, action bar sticks to viewport bottom, Display drops to 36px |
| `md` | 768px+ | Hero stays centered at `max-w-2xl`, workout view uses `max-w-3xl`, action bar inlines into card |
| `lg` | 1024px+ | Card hover effects unlock (combined with `(hover: hover)` media query); no layout change |

Claude's discretion (CONTEXT.md `<decisions> §Claude's Discretion`): use `md: 768px` as the single layout breakpoint for hero reflow. Anything `< 768px` is "mobile"; anything `≥ 768px` is "desktop." Two states only, no awkward tablet middle.

### 9.2 Landing hero composition (idle state)

**Desktop (`md`+):**
- Viewport-centered single screen, no scroll (CONTEXT.md D-04)
- Vertical rhythm: top spacer (`64px / 3xl`) → Display headline → `32px / xl` gap → Body subhead → `32px / xl` gap → URL input frame → `16px / md` gap → Primary CTA (full width within `max-w-2xl`) → `48px / 2xl` gap → footer (AI-disclaimer + credit)
- Total content occupies ~70% of viewport height, vertically centered

**Mobile (< 768px):**
- Same vertical order, tighter spacers: `48px / 2xl` top → headline → `24px / lg` → subhead → `24px / lg` → input → `12px / sm` → CTA → `32px / xl` → footer
- Hero may scroll on smaller phones (< 700px tall) — acceptable, no hard "single-screen" rule on mobile

### 9.3 Loading composition

- Same vertical center anchor as landing
- Header area collapses: no Display headline, instead a single Label `Building your workout` line at the top
- Stage list (4 rows, vertical, `8px` between rows) directly below the Label
- Skeleton cards (4 stacked, `16px` between) below the stage list
- Footer pinned to bottom

### 9.4 Success (workout) composition

**Desktop:**
- `max-w-3xl` container, top-aligned with `48px / 2xl` top padding
- `<WorkoutHeader />` at top — full width of container
- `24px / lg` gap
- `<ActionBar />` (sticky-top below header on scroll? **No** — inline in Phase 1, sits between header and exercises; sticky-on-scroll deferred to polish)
- `24px / lg` gap
- Exercise list — vertical stack of `<ExerciseCard />` / `<SupersetCard />` with `16px / md` between cards
- `48px / 2xl` gap
- Footer

**Mobile:**
- Full-width with `px-6` gutters
- `<ActionBar />` is **sticky-bottom** (fixed to viewport bottom edge, glass-treated, with `safe-area-inset-bottom` padding for notched devices)
- Exercise list scrolls; bottom action bar always reachable with thumb

### 9.5 Touch targets

All interactive elements ≥ 44px tap target (REQUIREMENTS OUTV-07). Specifically:
- Primary CTA: 56px height (intentionally larger per §2)
- Action bar buttons: 44px height, 44px min width for icon-only
- Form-cue expand toggle: full-width row of card (already > 44px tall)
- "Try again" / "Try another URL" buttons in error states: 44px height

## 11. Share Link Visual Contract (Phase-Specific Extension)

REQUIREMENTS SHRE-03, CONTEXT.md D-16/17/18.

**Encoding:** `?w=<lz-string-compressed-base64-url-safe>` where the payload is the validated `Workout` JSON plus `schema_version`.

**On hydration (recipient opens link):**
1. State machine jumps directly to `success` — no SSE stream, no loading state
2. Cascade animation is **disabled** on hydrated workouts (`shouldAnimateIn: false`) — feels instant, which is what "open a share link" should feel like
3. If payload was stripped per D-17 (>2KB), render inline notice above the workout header: `Share link omits form cues for length.` in Label style, `--text-muted`, with a small `Info` icon
4. If schema version is older but compatible: render normally; no notice
5. If schema version is newer/incompatible: render `<ErrorState />` with heading `This share link uses a newer version.` and body `Try pasting the original YouTube URL instead.`

**Visual continuity:** Hydrated workout looks **identical** to a freshly-extracted one (minus the cascade animation). Same glass, same spacing, same action bar (including the Share button — recipient can re-share, which generates a fresh link from the current rendered state).

## 12. SSE Event UI Mapping (Phase-Specific Extension — Cross-Reference)

This table is the canonical mapping from SSE event → UI state → visible change. Planner and executor consult this when wiring the reducer.

| SSE event | Reducer action | State transition | Visible change |
|-----------|----------------|------------------|-----------------|
| (none — CTA clicked, valid URL) | `{type:"submit", url}` | `idle → submitting` | Hero crossfades to loading view (~200ms); all 4 stage rows render in upcoming state |
| `{type:"stage", stage:"fetching"}` | `{type:"stage", stage:"fetching"}` | `submitting → streaming` | First stage row animates upcoming → active (pulse-dot, text emphasized) |
| `{type:"stage", stage:"transcribing"}` | `{type:"stage", stage:"transcribing"}` | `streaming → streaming` | Row 1 becomes completed (checkmark fade-in); Row 2 becomes active |
| `{type:"stage", stage:"analyzing"}` | same shape | `streaming → streaming` | Row 2 → completed, Row 3 → active |
| `{type:"stage", stage:"generating"}` | same shape | `streaming → streaming` | Row 3 → completed, Row 4 → active |
| `{type:"result", workout}` | `{type:"success", workout}` | `streaming → success` | Stage list + skeletons dissolve, header reveals, cards cascade per §6.2 |
| `{type:"error", code:"NETWORK", message}` | `{type:"error", code:"NETWORK", message}` | `streaming → error` | Stage list dissolves; ErrorState card replaces it with copy from §7.4 row 2 |
| `{type:"error", code:"NO_WORKOUT", message}` | `{type:"error", code:"NO_WORKOUT", message}` | `streaming → error` | ErrorState with copy from §7.4 row 3 |
| `{type:"error", code:"RATE_LIMITED", message}` | `{type:"error", code:"RATE_LIMITED", message}` | `streaming → error` | ErrorState with copy from §7.4 row 4 |

**No-`setTimeout` rule:** Every UI state change above is driven by an SSE event arrival or a synchronous user input (click, type). Zero `setTimeout` in `<ExtractFlow />`. The mock service emits events on a `setTimeout` schedule *server-side* (within the Node route handler); the UI is mode-agnostic.
